Telegram messages · a sandbox for HTML widgets · how it works

widget-sandbox architecture

A bot sends an ordinary HTML file with a script into the chat. widget-sandbox runs it whole, but in a cage: the script executes in the small QuickJS engine against its own copy of the DOM, with no screen and no network. Everything the script changes in that copy becomes a list of operations, the list is checked against allowlists, and only then does trusted code apply it to the real page in the system WebView. Three zones, one trust boundary, the same three JS files on five platforms.

The idea in three sentences

  • The widget thinks it is in a browser. It has document, events, timers and canvas. Nothing has to be rewritten.
  • But its browser is not real. It is a DOM inside QuickJS on a dedicated thread. It cannot draw and it cannot reach the network. All it can do is report what changed.
  • A real WebView draws, but it receives validated operations, not HTML. Between the sandbox and the screen stands a validator that passes only known tags, attributes and CSS properties and strips every address except embedded images.

Three zones

bot contentshared JS, identical on every platformper platform, swappable

There is one trust boundary: between the first and the second zone. Everything that leaves QuickJS is hostile until the validator says otherwise. The renderer is protected once more in case the validator fails: it refuses forbidden tags on its own, and CSP plus request blocking keep the page off the network even if something slips through.

Every message is flat JSON that can be logged and replayed in tests. Nodes are addressed by numeric ids handed out by the sandbox; the renderer never receives an HTML string, only "create a div element with id 17". On the web, sync queries go through SharedArrayBuffer and Atomics.wait; natively through a semaphore. The sandbox thread is the one that waits, never the main thread.

Lifecycle and limits

Every decision about how much the widget may do is made by the glue, that is by trusted code. The sandbox learns about it after the fact: a frame did not arrive, a timer fired late, an "out of memory" exception.

What the widget author sees

Works

  • All the markup and CSS WebKit knows: grid, flex, custom properties, transition, @keyframes, @container, inline SVG, forms, <details>, <dialog>.
  • Inline scripts in document order, ES2023, Promise, timers, rAF, MutationObserver, ResizeObserver, Intl, crypto.randomUUID.
  • DOM API: selectors, innerHTML, classList, dataset, forms with value and checkValidity, size measurements, getComputedStyle.
  • Canvas 2D (no bundled libraries since widget profile 1).
  • The chat theme through prefers-color-scheme, light-dark() and TelegramWidget.onTheme.

Does not work, by design

  • Any network: scripts, images, fonts, stylesheets, fetch, WebSocket, WebRTC. Images and fonts only as data:.
  • WebGL, Web Audio, workers, navigation, window.open (replaced by a host dialog).
  • localStorage lives only as long as the widget does.
  • preventDefault() from the sandbox is asynchronous: navigation and submit are always cancelled; the first checkbox toggle or text input may show its native behaviour for one frame.
  • Intl.formatToParts is not there yet.

This list is published as the runtime profile (docs/widget-runtime-profile.md). A model that gets it in the tool description generates widgets that pass without a single blocked request: 20 of 20 in the test.

What this architecture gives

  • The format stays standard. A widget is an ordinary HTML file, written by models, bots and people with no knowledge of our API. 40 of 40 generated widgets passed without a rewrite.
  • The picture is real. The system WebView draws, so the widget looks the way its author saw it in a browser. The comparison with native rendering is pixel-level and automatic.
  • Restrictions are policy, not incapacity. The allowlists can be narrowed to any profile in a day and widened back. Whatever a bot throws at it, only the list gets through.
  • Foreign HTML is never parsed in the messenger's process. The sandbox parses it; WebKit receives operations and works in its own isolated process. A renderer bug lands in a process that is already sandboxed.
  • There is no network by construction. Network objects do not exist in the sandbox, the validator passes no addresses, the renderer blocks requests, the test canary stays silent. Four independent layers.
  • One engine everywhere. The same bundles and the same limit policy on five platforms; a difference between platforms is a bug with a fixture, not a quirk.
  • Parts are swappable. The engine, the renderer, the policy, the Intl provider. On tdesktop the renderer can be a native backend; the format and the trust boundary do not change.
  • Animations are free. CSS transitions and keyframes run on the compositor, 0 ms of script. A JS frame sends a diff of a few operations, not the whole page.

What it costs

  • Memory. 1.8–3.7 MB per widget runtime (DOM, parser, library) plus a WebView per visible widget. The WebView is the main cost. Hidden widgets are already paused; replacing them with a snapshot and killing the runtime is not done yet.
  • Startup. About 40 ms to load the DOM bundle in a release build, 150 ms in an iOS debug build. Bytecode precompilation should bring it to a few milliseconds; still open.
  • Sync measurements. Every getBoundingClientRect or getBBox is a hop between threads. D3 with hundreds of measurements in a loop is the known bottleneck, covered by a cache until the next mutation, but not free.
  • More code at the boundary. The browser API shim, the validator, the CSS sanitizer and the URL policy are 6,300 lines of TypeScript that have to follow what widgets use. "A string in, a string out" is simpler.
  • Asynchronous preventDefault. The sandbox cannot cancel a native action in the same frame. Navigation and submit are always cancelled; the rest by learned cases.
  • Errors are not visible to the user. Widget exceptions go to the diagnostics panel; the badge and restart exist only for killed runtimes.
  • The web client needs cross-origin isolation for SharedArrayBuffer, which may interfere with other embeddings.
  • Nothing where there is no WebView. The Telegram Desktop chat has no renderer; there is the sandbox core and two paths: the Web App window, or a native backend that still has to be written.

Working rules: the shim is fixed in general, never for one widget; a regression in the corpus is a shim bug until proven otherwise; the invariants (JS only inside QuickJS, everything from the sandbox is hostile, the renderer receives only validated operations, no URLs other than data: and #, no network, defence in depth) are not relaxed without discussion.
