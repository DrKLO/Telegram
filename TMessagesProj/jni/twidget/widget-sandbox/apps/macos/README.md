# macOS implementation

The macOS port is the iOS Swift package compiled for AppKit: `WidgetSandbox`
in [`packages/ios/`](../../packages/ios/README.md) already builds for `.macOS(.v13)`, and the three
JavaScript bundles (sandbox shim, trusted validator, renderer with the `webkit`
transport) are byte-for-byte the ones iOS ships. WebKit's API is the same on
both platforms; what differs is the view layer, and that is a handful of
`#if os(macOS)` branches in three files.

```
macos/
  DemoApp/
    project.yml              xcodegen project: SwiftUI app for macOS 13+, sources and corpus from apps/ios/DemoApp
    Info.plist               generated by xcodegen (local networking for the canary)
packages/ios/Sources/WidgetSandbox/
  Platform.swift             PlatformView = UIView | NSView, screen scale
  RendererWebView.swift      WKWebView knobs per platform (see below)
  WidgetHost.swift           WidgetContainerView: UIView (didMoveToWindow) | NSView (window + occlusion)
  WidgetView.swift           UIViewRepresentable | NSViewRepresentable, shared WidgetModel
packages/ios/Tests/WidgetSandboxTests/
  TestWindow.swift           UIWindow | NSWindow helper for the WKWebView tests
apps/ios/DemoApp/Sources/
  ReferenceWebView.swift     reference mode (dev tooling): the same file rendered natively, no sandbox
  NativeRenderer.swift       Blitz / litehtml renderer prototypes (dev tooling), AppKit branch: mouse → one pointer, 60 Hz timer
  CompareRunnerView.swift    sandbox vs reference timing over compat + generated (--autorun compare)
```

## Build and run

```bash
corepack pnpm build:macos            # = build:ios: bundles → packages/ios/Sources/WidgetSandbox/WidgetJS, corpus → apps/ios/DemoApp/Corpus
cd apps/macos/DemoApp && xcodegen generate # regenerates TwidgetDemoMac.xcodeproj (brew install xcodegen)
open apps/macos/DemoApp/TwidgetDemoMac.xcodeproj
```

Package tests natively (no simulator):

```bash
xcodebuild test -scheme WidgetSandbox -destination 'platform=macOS'
```

The Blitz and litehtml renderer prototypes are frozen (`packages/ios/README.md`, "Native renderer prototypes"): like
the iOS demo, this one builds and links them only with `TW_NATIVE_RENDERERS=YES` on `xcodebuild`, and then the
pre-build script phases need rustup's `cargo` and Homebrew's `cmake` + `ninja`.
The demo is ad-hoc signed, not sandboxed (it must reach the canary itself)
and never distributed. Its runners can be driven from a shell with a launch
argument, like the Android demo's `--es autorun`; each writes a JSON report to
`~/Library/Application Support/org.telegram.widgetsandbox.TwidgetDemoMac/` and
quits:

```bash
cd apps/macos/DemoApp && xcodebuild build -project TwidgetDemoMac.xcodeproj -scheme TwidgetDemoMac -destination 'platform=macOS' -derivedDataPath /tmp/twidget-mac
APP=/tmp/twidget-mac/Build/Products/Debug/TwidgetDemoMac.app/Contents/MacOS/TwidgetDemoMac
corepack pnpm canary &                 # the attack runner asks it for hits
"$APP" --autorun attacks               # → attack-report.json   (hits must be 0)
"$APP" --autorun generated             # → generated-report.json (40 widgets)
"$APP" --autorun compat                # → compat-report.json    (21 widgets)
"$APP" --autorun htmlbubbles           # → htmlbubbles-report.json (116 Telegram demos ported to classic widgets; build with -configuration Release, the Debug QuickJS is too slow for their boot under the 500 ms wall-clock slice)
"$APP" --autorun pause                 # → pause-report.json     (window minimised ⇒ frames stop)
"$APP" --autorun compare               # → compare-report.json   (sandbox vs native WebKit, wall time to loaded)
"$APP" --autorun generated --blitz     # the same on the Blitz renderer prototype (a TW_NATIVE_RENDERERS=YES build); --litehtml for litehtml, --webview back (the choice is persisted)
```

## Reference mode (dev tooling, never a product path)

Like the web prototype's `?reference=1`, the corpus browser has a
**Reference** toggle: the same file is rendered a second time natively by
WebKit — no QuickJS, no validator, no renderer protocol — so output and speed
can be compared against what the engine does on its own. The demo implements it
in `ReferenceWebView.swift`, outside the `WidgetSandbox` package: a doctype is
added (no library is bundled, so a CDN script fails as in the sandbox), and the page is served from a private `tgref://` scheme that refuses
every other URL, with the web dev server's `REFERENCE_CSP` (`connect-src
'none'`, `script-src 'self' 'unsafe-inline' 'unsafe-eval'`), the http(s)/ws(s)
content rule list and every navigation cancelled. The toggle is hidden for
`attacks/`, and `--autorun compare` never loads that corpus: a reference page
runs the widget's own scripts with the full DOM, there is no sandbox to test.
Both bubbles show "loaded in N ms" with the same definition — wall clock from
creating the host (`WidgetHost`, or the reference's `WKWebView`) to `loaded` /
the `load` event — so the two can be compared at a glance. The reference bubble
adds the page's own clock (`loadEventStart` and DOMContentLoaded from navigation
start), which excludes creating the web view and its process and is therefore
much smaller, plus uncaught errors.

`--autorun compare` loads every compat and generated widget both ways and
writes `compare-report.json` (per widget: sandbox wall time to `loaded` and
the engine's JS time; reference wall time to the `load` event and the page's
own `loadEventStart`). Debug build (quickjs-ng at `-O0`), one run, medians:

| Corpus | Sandbox: wall to loaded | Sandbox: JS time | Reference: wall to load | Reference: page's own load event | Ratio |
|---|---|---|---|---|---|
| compat (21) | 215 ms (max 484) | 19 ms | 105 ms (max 156) | 6 ms | 2.3× |
| generated, with profile (20) | 240 ms (max 325) | 33 ms | 107 ms (max 151) | 21 ms | 2.3× |
| generated, without profile (20) | 236 ms (max 365) | 32 ms | 107 ms (max 221) | 22 ms | 2.2× |

Reading it: both wall times include creating a WKWebView and its web content
process (~100 ms, the whole reference number); the sandbox adds the QuickJS
boot (evaluating ~500 KB of sandbox bundle from source, the bulk of the
difference; the precompiled `.qbc` bundles have since halved it), the validator
round trip and the renderer handshake. The widget's own script work is 20–35 ms
in QuickJS against 7–21 ms natively. The numbers are from a debug build and
should be re-measured in release before being quoted.

One widget fails in reference mode and passes in the sandbox: `d3-bar`
calls `getBBox()` on an SVG `<text>` it has just appended, synchronously while
the document is still being parsed, and WebKit throws `NotFoundError: The
object can not be found here.` there (a bare WKWebView reproduces it; the same
call succeeds once the page has loaded, and Chromium — the web reference —
never throws). The sandboxed widget is unaffected because its layout queries
are answered by the renderer against a laid-out document after the ops flush.

## What differs from iOS

| iOS | macOS |
|---|---|
| `UIView` container, `didMoveToWindow` ⇒ visible | `NSView` container; visible = in a window **and** `NSWindow.occlusionState` contains `.visible` (minimised, fully covered or on another Space counts as hidden, like a background tab). `occlusionState` is trusted only once the window server has reported on the window; before that `isVisible` decides — an xctest process never finishes launching `NSApplication` and would otherwise count every window as hidden |
| `overrideUserInterfaceStyle` for the theme | `webView.appearance = NSAppearance(.aqua / .darkAqua)` drives `prefers-color-scheme` |
| `isOpaque = false`, clear `backgroundColor`, scroll view disabled | `drawsBackground = false` (KVC; the public `underPageBackgroundColor` only tints past the document's end); no scroll view: the host sizes the view to the content, and wheel events over a non-scrolling document reach the enclosing scroll view |
| — | `RendererWKWebView` removes the context menu (`willOpenMenu`): Reload, Open in New Window, Download, Inspect Element are navigations we cancel anyway or tooling a bubble must not expose |
| — | `runOpenPanelWith` answers `nil`: `<input type=file>` never opens a file dialog, the widget gets nothing from the disk |
| `UIScreen.main.scale` | `NSScreen.main.backingScaleFactor` as the initial `devicePixelRatio`; the renderer reports the real one with its first `size` |
| `allowsInlineMediaPlayback` | iOS-only setting, skipped |

Everything security-relevant is unchanged: the custom scheme handler serving
exactly one document, nonce CSP as header and `<meta>`, the content rule list
blocking `http(s)`/`ws(s)`, non-persistent data store, every navigation
cancelled in `decidePolicyFor`, `window.open` → nil, the document-start script
deleting the network APIs, the trusted validator between engine and renderer,
and QuickJS on its own `JSThread` with the 8 MB stack. The macOS demo is not
App-Sandboxed; a host app that is, without `com.apple.security.network.client`,
would add one more platform barrier in front of WebKit's networking process,
but nothing here relies on it.

## Verified (macOS 26.5, Xcode 26.6, Apple silicon)

- Package tests natively: 21 tests green (engine, QuickJS thread pinning,
  trusted validator, renderer in a real WKWebView, WidgetHost end-to-end:
  validator diagnostics, CSSOM attacks reported as blocked, killed widget keeps
  its last render). `testRemovingTheViewFromTheWindowPausesTheWidget` is iOS
  only: under `xcodebuild test` the xctest process gets no window-server
  occlusion events, so WebKit keeps the page `hidden` (no animation frames,
  timers at 1 Hz — checked with a bare WKWebView in the same kind of process);
  the same scenario runs in the demo as `--autorun pause`.
- The same 22 tests still pass on the iPhone 17 simulator (iOS 26.5) after the
  AppKit changes.
- Demo runners (debug build, quickjs-ng at `-O0`):

| Runner | Result |
|---|---|
| attacks (89 files) | canary hits **0**; 237 blocked diagnostics; one widget dead by design (`fallback-at-boot`, CPU limit) |
| generated (40) | 40/40 load without errors; JS time median 97 ms, max 875 ms |
| compat (21) | 21/21; median 19 ms, max 91 ms |
| pause | see `pause-report.json` after `--autorun pause`: frames flow with the window visible, stop while it is minimised, resume after restore; the widget sees `visible,hidden,visible,` |

## Not done / next

- Same open items as iOS: `Intl.formatToParts`, snapshot-and-drop of hidden
  runtimes, pentest of the WebKit blockers beyond the attack corpus.
- Keyboard focus and the Tab order between native chat chrome and a widget's
  form controls have not been designed; WKWebView takes focus like any NSView.
- A chat list with many bubbles: the demo shows one widget per screen; the
  product's scroll-visibility reporting (`setVisible`) is the host's job as on
  iOS and Android.
